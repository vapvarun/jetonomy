# Security review: Jetonomy 2.0.7

Scope: everything shipped since v2.0.6, Free and Pro: access-rule editing and gating, address-field validation,
host-plugin moderation filters, the case-variant redirect, the Divi Theme Builder integration, vote/reputation
consolidation, admin contrast, translations.

## G1 mechanical sweep

`security-sweep.sh --baseline v2.0.6`. No CRITICAL patterns in either plugin.

- Pro: identical counts to 2.0.6.
- Free: +2 `sql-direct-interpolated`, +2 `nonce-only-auth`, +1 REST route. All five reviewed:
  - `includes/db/migrations/class-migration_2_0_7.php`: two `UPDATE` queries interpolate only the prefixed table
    name; every value is a literal. No request data.
  - `includes/admin/ajax/class-spaces-handler.php`: the new `ajax_update_access_rule()` and
    `ajax_search_membership_levels()` check `current_user_can( 'jetonomy_manage_spaces' )` on the line after the
    nonce. The sweep counts the nonce call, not the missing capability.
  - `PATCH /jetonomy/v1/access-rules/{id}`: `REST_Auth::auth_mutation( 'jetonomy_manage_spaces' )`, declared in
    `audit/route-authority.json`; a subscriber gets 403 (`AccessRuleGrantsEditTest`).

## G2 authorisation

`RouteAuthorityTest` (Free) and `RouteAuthorityProTest` run in the unit and combo suites and pass: every registered
route is declared with its audience. New in 2.0.7 and checked as a second member:

- Access rules: create, update grant and delete are admin-only (403 for a subscriber).
- Privacy: on a private community a signed-out visitor is denied every action (`Permission_Engine`), which closes
  guest answers from Pro poll, reaction and attachment-download routes (`Visibility::rest_check`).
- Silenced and banned members cannot create a space on any create path, including BuddyPress group forums.
- A member suspended in BuddyNext is read-only (`jetonomy_user_is_silenced`): read 200, reply, vote and new topic
  403 `jetonomy_user_silenced`, verified end to end with BuddyNext 1.2.8 on 2026-10-30.

## G3 reviewed diff

- Address fields: `\Jetonomy\http_url()` is the one check for a typed address (http/https, IDN host). REST
  `cover_image` and `avatar_url` no longer declare `format => uri`, because WordPress ran `esc_url_raw()` first and turned
  `javascript:` / `data:` into an empty string, which the handler read as "clear the image". Those values are now
  refused with 400 and the stored image kept (`UnsafeImageAddressTest`). Pro SEO Pro, AI provider and branding icon
  addresses refuse the same way.
- Case-variant redirect: `wp_safe_redirect()` to `home_url()` of the lower-cased path; GET and HEAD only; the
  query string is passed through unchanged; `/invite/` tokens are left as typed.
- Space feed: text nodes drop XML-forbidden control characters before `esc_xml()`.
- Divi integration: swaps the queried object for an empty non-hierarchical post during layout renders and
  restores it afterwards; no input is read.
- Removed in 2.0.7 before release: the `jetonomy_user_is_banned` filter (never shipped, no consumer) and the
  `full` access grant (never gave more than participate; `full` input is saved as participate).

## Scanner-visible but safe

- Interpolated SQL in models and migrations: table names from `\Jetonomy\table()` / `$wpdb->prefix`, values
  through `prepare()`.
- `check_ajax_referer()` hits: every Jetonomy AJAX handler follows it with `current_user_can()`.

## Not blocking, recorded

- Unchanged since 2.0.6 and carried: the 23 Free / 6 Pro files without a direct-access guard (class files that
  only declare classes), and Pro's attachment download `readfile`: the path is `get_attached_file()` of the
  attachment id stored on the link row (never taken from the request), served only after `viewer_can_read_link()`,
  with 404 for unknown or unreadable links.
